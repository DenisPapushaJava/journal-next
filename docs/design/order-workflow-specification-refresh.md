## Основание и границы

Пользователь уточнил:

- после подготовки проектов технолог делает раскладку и выгружает отчёты;
- готовая HTML/PDF-спецификация сохраняется рядом с файлом проекта;
- затем нужно подтянуть спецификации в расчёт из карточки заявки;
- часть проектов ещё может не иметь спецификаций;
- CAM может перезаписать исправленную спецификацию под тем же именем;
- уже сделанный расчёт требуется обновить по аналогии с редактором Journal;
- поиск/обновление должны сокращать ручную работу технолога.

Сохраняются [подготовка проектов](order-workflow-project-preparation.md),
привычные имена и правило один проект — одна спецификация. Переделка под
другой станок остаётся предложенным отдельным вариантом позиции. Обновление
отчёта того же проекта создаёт редакцию его спецификации, не новую позицию.
Подбор не генерирует отчёт средствами CAM и не конвертирует её проекты.

Ниже предложены UX, хранение и проверки. Автосохранение без просмотра,
файловые наблюдатели, архив исходных отчётов и точное размещение новых
настроек не считаются уже утверждёнными/реализованными.

## 1. Предлагаемый основной сценарий

1. Технолог возвращается в карточку заявки и нажимает «Обновить спецификации».
2. По данным заявки программа получает папки выбранных проектов и новых
   незавершённых вариантов; проверяет только соседние HTML/HTM/PDF.
3. Однозначные отчёты распознаются, сопоставляются и разбираются автоматически.
   Пустые исходные rcam/Dsp/aucb/dig не считаются готовыми отчётами.
4. В одной сводке видны новые/изменённые/неизменённые/ожидаемые документы
   и строки, требующие проверки. Нет отдельного модального окна на каждый файл.
5. Новые параметры и цена показываются в предварительном просмотре.
   Ручное вмешательство нужно для неоднозначностей, материала AWJC,
   неизвестных тарифов и противоречащих ручным правкам полей.
6. «Сохранить готовые (N)» фиксирует выбранные проверенные строки одним
   действием. Проекты без отчёта остаются ожидающими, с ними можно продолжить
   позже. Повторная команда не создаёт дубли уже принятого документа.

Автоматизируются поиск, сопоставление, разбор, сравнение и предпросмотр.
Точное сохранение одним действием сохраняет осознанный выбор технолога
при изменении стоимости/раскладки. Отдельные согласования на каждый
однозначный корректный файл не требуются.

Следующее удобство после проверки основного сценария — тихая проверка
при открытии карточки/возврате из CAM, с подсказкой «Есть новые спецификации».
Она использует тот же механизм и не переписывает ввод/расчёты/письмо.
Постоянный обход общего архива и обязательный watcher для первого этапа
не нужны. Фактическое поведение автообнаружения ещё обсуждается.

### Принято к следующей доработке: комплектность заявки · 24.10.2026

Пользователь выбрал только наглядную сводку готовности в карточке заявки,
например «Из 5 проектов: 3 рассчитаны, 1 ожидает отчёт, 1 требует проверки»,
с быстрым переходом к соответствующим позициям. Нынешние ProjectsStatus и
проверки принятия отчётов дают основу; новые сводка и переходы не реализованы.
Переход сохраняет черновики и текущий ввод. Варианты переделки не увеличивают
число самостоятельных позиций заявки; непроверенная переделка учитывается
как требующая решения по соответствующей позиции.

При реализации различать отсутствие принятой спецификации, подтверждённое
отсутствие отчёта при подборе и невозможность проверки папки/файла. До первого
подбора нельзя выдавать отсутствие записи в БД за отсутствие файла; после
ошибки доступа нельзя показывать «отчёта нет». Сводка показывает известное
состояние, без обещания непрерывного наблюдения за диском. Конкретные подписи,
группы и UX перехода уточняются на следующем этапе.

Остальные предложенные по сторонней ACCDE функции сейчас не актуальны:
фиксация редакций всей заявки, создание заявки на основе другой, групповые
правки, общие условия для менеджера. Их реализация не входит в этот этап.

## 2. Состояния проверки и основные случаи

| Случай | Предлагаемое поведение |
| --- | --- |
| Отчёт ещё не создан | «Ещё нет»; пустые поля/неизвестная цена не становятся нулями |
| Найден первый готовый отчёт | Автоподбор в подготовленный проект, предпросмотр и сохранение первой редакции |
| Принятый файл побайтно прежний | «Без изменений»; без новой редакции/пересчёта/записи |
| Имя и путь прежние, байты новые | «Изменена»; разбор, diff и обновление той же спецификации |
| Байты новые, расчётные итоги совпали | Отдельно показать обновление документа: могли измениться детали/раскладка |
| Несколько подходящих разных отчётов | Выбор кандидата, без угадывания по самому новому mtime |
| Файл ещё пишется/занят/пустой | «Пока не удалось прочитать»; следующая проверка, прежний расчёт сохраняется |
| Папка недоступна | «Проверка не выполнена», а не «спецификации нет» |
| Файл удалён/перемещён после принятия | Не удалять заявку/расчёт/историю; предложить уточнить источник |
| Неизвестный PDF/скан/ошибка структуры | Причина у строки; остальные документы остаются в сводке |
| Другой станок/чужой проект внутри отчёта | Не менять существующий вариант молча; явное назначение/новый вариант |
| Есть ручные правки | Сохранить черновик, показать только противоречия |
| Коллега успел сохранить | Проверить версии; равный уже принятый результат — no-op, иной — конфликт с сохранением ввода |
| Готовое письмо уже отредактировано | Отметить устаревание, сохранить ручной текст |

Это состояния получения данных, не производственные статусы «В работе».
Ожидание одного отчёта не блокирует принятие остальных готовых. Частичный
итог явно отмечен; полный расчёт заявки не показывается, пока выбранные
позиции не готовы. Незавершённая переделка под другой станок видна отдельно.

## 3. Сопоставление и ограничение поиска

Главный контекст — OrderId, позиция, конкретный ProjectId и сохранённая
папка проекта. Не сканировать все годы «Расчёта заявок» и не выбирать запись
по одному времени/имени. Имена CAM/спецификаций остаются привычными.

Уже принятый путь отчёта проверяется первым. Для первого подбора:

- известная папка проекта и допустимые контейнеры ограничивают кандидатов;
- профиль распознавания проверяет структуру, а заголовок — исходное имя
  проекта, номер/дату, станок и прочие существенные поля;
- известные суффиксы экспорта учитываются профилем; произвольное удаление
  подчёркиваний/дефисов/расширений ради совпадения не допускается;
- станок и толщина сверяются с подготовкой; материал и категория первого
  отчёта заполняют расчёт без сравнения с подготовкой; при обновлении
  проверяются изменения относительно принятой версии и ручных правок;
- неоднозначность остаётся видимой даже при одинаковых именах;
- при ручном выборе отчёта связь с этим вариантом запоминается явно.

Карта раскроя, чертёж или другой PDF в той же папке не становятся
спецификацией по расширению. Отказ распознавания постороннего документа
не является техническим сбоем всего подбора. Удаление/переименование рабочих
файлов по результатам поиска не выполняется.

Старые невыбранные варианты по умолчанию не перечитываются вместе со всей
историей. Их обновление открывается в явном контексте варианта. Новый отчёт
не переключает выбранный станок или вариант заявки автоматически.

## 4. Файл с тем же именем и новая редакция

Имя, размер и время изменения не доказывают равенство содержимого.
У принятого отчёта сохраняются исходное имя, профиль, размер и SHA-256.
Для проверки берутся одни зафиксированные байты: их же разбирает парсер
и по ним же считается хеш, без двух независимых открытий для этих задач.

Совпадение хеша с принятым снимком данного проекта означает неизменный
документ. При явной повторной проверке новые байты должны обнаруживаться
даже при прежних имени, размере и mtime. Метаданные пригодны как подсказка/
кеш, но не единственное основание «Без изменений».

Уточнение пользователя: можно ли вместо содержимого сравнивать дату изменения.
Одна дата не выбирается критерием равенства. Она может сохраняться при
копировании/задаваться программой, иметь ограниченную точность и меняться
при прежних байтах. Используются LastWriteTimeUtc/размер как подсказка,
хеш — для проверки байтов. Хеш считается по ограниченному снимку потоком,
без загрузки всех проектов в память. При каждом явном «Обновить» дата
не позволяет пропустить проверку содержимого и ошибочно подтвердить актуальность.

«Без изменений» относится к отчёту, не отменяет ручной dirty-правки формы.
Ручной коэффициент можно сохранить отдельно даже при прежнем файле.

Другие байты требуют проверки новой редакции. Равенства длины, веса,
пробивок и цены недостаточно, чтобы объявить отчёт прежним: могли поменяться
состав деталей, чертежи или раскладка. Для первого надёжного варианта новый
принятый документ получает новую редакцию даже при прежней цене.
Автоматический пропуск только «печатных» различий возможен позже лишь после
проверенного сравнения всего существенного содержимого, не одних итогов.

Равный файл, переименованный/перемещённый в контексте того же проекта,
не требует новой редакции расчёта; связь с новым источником меняется явно.
Равные байты у разных проектов не объединяют их идентичность.

Нужен проверяемый способ получить законченный снимок при экспорте CAM:
обработка блокировок, замены файла и ограничение размера/времени чтения.
Два одинаковых значения mtime не являются доказательством окончания записи.
При сомнении файл остаётся ожидающим, не заменяет прежние принятые данные.

Перед применением проверяется, что исходник соответствует предпросмотру;
изменившийся кандидат возвращается на обновление diff. Файл может меняться
и после проверки: Access не фиксируется атомарно с внешней CAM. Гарантия —
сохранён расчёт именно по принятому снимку; новую выгрузку покажет следующая
проверка. Не обещать «всегда последнюю» внешнюю редакцию без протокола CAM.

Если изменён сам CAM-проект, но отчёт не выгружен, автоматически получить
новую спецификацию нельзя. Время проекта может быть подсказкой, но не
доказательством актуальности/устаревания отчёта.

## 5. Сохранение ручных правок

Разделяются исходный распознанный снимок, эффективные сохранённые значения
и новый распознанный снимок. Менеджер/заказчик/БЛЦБ/ответственный не берутся
из заменяемого отчёта. Ручной коэффициент Workflow не вычисляется заново
из прежнего алгоритма Journal.

Если исходный снимок A не сохранён, его не угадывают по текущим значениям.
Показывается B → C и явно проверяются ручные поля. Новые импорты должны
сохранять распознанное основание для следующего сравнения.

Комментарий, выбранные работы/пометки и другие собственные данные сохраняются
до явной правки. Для полей, которые технолог мог исправлять после импорта,
предлагается сравнение трёх значений:

| Было в прежнем отчёте A | Сохранено технологом B | Новый отчёт C | Действие |
| --- | --- | --- | --- |
| B = A | Ручной правки нет | C изменилось | Предложить C автоматически |
| B отличается от A | Есть правка | C = A | Сохранить B |
| B отличается от A | Есть правка | C = B | Значения совпали, противоречия нет |
| B отличается от A | Есть правка | C отличается и от A, и от B | Показать выбор только этого поля |

Неизвестное C не подменяется прежним известным A/B как скрытый fallback.
Если поле обязательно, строка требует проверки/исправления.
Материал AWJC по-прежнему не подтверждается фокусом, раскрытием, именем
файла или простым совпадением со справочником. Правило подтверждения новой
редакции должно сохранять контракт профиля и ручную корректировку.

Если в форме уже есть несохранённый ввод, сканирование может подготовить
отдельный кандидат, но не меняет поля под курсором. Применение к спорной
строке требует разрешения её правок; готовые другие строки доступны.
Закрытие/смена заявки отменяют применение позднего результата.

## 6. Цена при обновлении

- При изменении метров/пробивок пересчитывается текущий предпросмотр
  с сохранённым ручным коэффициентом.
- Если станок/категория/толщина прежние, по умолчанию сохраняется использованный
  снимок тарифа. Само перечитывание отчёта не обновляет его до последних цен.
- При изменении тарифного ключа прежний тариф не подходит: показывается
  соответствующий сохранённый тариф нового ключа, неизвестный — требует ввода.
- Другой станок относится к переделке/выбору варианта, а не скрытому изменению
  исторического CAM-файла.
- «Обновить тариф» остаётся явным действием. Старые суммы и версии неизменны.
- Если показатели формулы прежние, новый документ может сохранить прежний
  снимок расчёта и показать «Документ обновлён, цена без изменений».
- Новые правила округления/минимума этим сценарием не вводятся.

До сохранения видны краткие «было → стало»: например, метры, пробивки,
количество, материал и итог. Технологу не показываются хеши/технические ID
как обязательный этап обычной работы.

## 7. Частичная готовность и одна запись

Сканирование — чтение/предпросмотр. Не создаются записи истории или служебный
DDL от простого открытия карточки. Кандидаты живут в сеансе до применения;
долговременный черновик будет отдельным решением.

«Сохранить готовые» принимает только выбранный проверенный набор, а не все
ожидаемые проекты заявки. Отсутствующие/занятые/непроверенные строки не
включаются автоматически. По выбранному набору выполняется одна транзакция:
версии, расчёты, работы, ссылки на снимки, события, текущие версии и маркеры.
Не заменять её циклом независимых Save без ясного итога.

Перед записью сверяются базовые версии всех выбранных спецификаций и
соответствие кандидатов. Конфликт выбранной строки не допускает скрытого
частичного commit группы. Предпросмотр всех строк сохраняется; пользователь
может разрешить конфликт либо исключить строку и сохранить остальное.
Порядок блокировок и command_id — по [проекту запросов](order-workflow-queries.md).

Если коллега уже принял тот же снимок и полностью тот же эффективный
результат, возможен no-op «Уже обновлено». Одного равного хеша недостаточно
для игнорирования чужого коэффициента/пометок. Иное состояние — конфликт.
При неизвестном commit проверяется квитанция, автоматического повтора нет.

Готовое ручное письмо не формируется заново при обновлении расчётов.
Показывается устаревание; текст остаётся до явного формирования.

## 8. История исходных отчётов — предложение

После перезаписи рабочего PDF/HTML прежние байты по тому же пути потеряны.
Для восстановления прежней спецификации предлагается автоматически сохранять
неизменяемый снимок каждого принятого отчёта в общем архиве документов.
Пользователь также предложил автоматическое сохранение принятых HTML/PDF
и уточнил критерий изменения; путь/сроки архива пока не выбраны.
Привычное имя файла сохраняется внутри отдельного каталога снимка/редакции.
Метаданные/хеш в БД сами по себе байты не восстанавливают.

Байты отчётов хранятся вне MDB/ACCDB; в БД только ссылки/метаданные/хеши.

Это предложение касается HTML/PDF отчёта; все DXF, программы станка и
CAM-проекты при каждой проверке не копируются. Место/сроки/права архива
ещё требуют решения. Если архив не принят, UI обещает историю параметров/
цен, но не гарантирует открытие прежнего файла.

Подготовка снимка выполняется до короткой транзакции БД. В БД связываются
только готовые проверенные байты. Неудача/неизвестный commit не приводит
к удалению чужих файлов; очистка собственных неподтверждённых снимков
должна учитывать квитанции и иметь отдельный безопасный порядок.

## 9. Следствия для модели и запросов

Возможные данные, точный DDL пока не утверждён:

- связь спецификации с известным рабочим путём отчёта и row_version связи;
- принятый source_snapshot_id/хеш и исходное имя в версии;
- профиль/версия парсера и исходные распознанные значения для сравнения A/B/C;
- эффективные параметры/цена/работы остаются типизированными основными данными.

Источник распознавания не подменяет таблицы расчётов универсальным JSON/EAV.
Физическое представление типизированного исходного снимка выбирается при DDL;
поисковые/тарифные ключи остаются нормальными колонками. Обновление парсера
не пересчитывает историю автоматически; кеш разбора учитывает его версию.

Кандидаты чтений:

| Код | Состав |
| --- | --- |
| Q11 | Папки/известные пути отчётов выбранных и новых незавершённых вариантов одной заявки |
| Q12 | Базовые текущие версии/снимки/ручные значения только найденных кандидатов |

Данные получаются пакетно, без SQL на каждый распознанный параметр и без
загрузки всей истории. Соседние отчёты читаются ограниченным числом задач;
кандидат первого этапа — до двух одновременно, с лимитами файла/группы.
Повторные сигналы объединяются; одно чтение не запускает второе поверх себя.

FileSystemWatcher при дальнейшем добавлении — подсказка на перепроверку,
не источник истины: Created может прийти до завершения копирования,
операции могут давать несколько событий, буфер — переполняться.
Ручная команда остаётся полноценной сверкой независимо от watcher.

## 10. Проверки до реализации в рабочем приложении

- Часть отчётов отсутствует; оставшиеся принимаются вместе без нулевых цен.
- Повторный подбор прежних байтов не создаёт версии.
- Исправленный файл под тем же именем, включая равные размер/mtime.
- Другие детали/раскладка при прежних итоговых числах.
- Файл меняется во время чтения, после предпросмотра и около commit.
- Нулевой/занятый/незаконченный/чужой PDF, несколько подходящих отчётов.
- Удаление/перемещение источника, отказ одной папки и всего SMB.
- Четыре случая A/B/C, ручной коэффициент, AWJC/пометки/комментарий.
- Смена категории/толщины, отсутствие тарифа, явное обновление цен.
- Два клиента принимают одинаковый/разный результат; rollback группы,
  неизвестный commit и повтор command_id.
- Несохранённая форма, закрытие/смена заявки, поздний ответ, сохранение письма.
- Windows/Jet либо ACE и настоящая общая папка; Linux-прототип этого не доказывает.

Пока это сценарий, не выполненные проверки. Реальные образцы остаются
приватными и не изменяются; будущие автоматические проверки синтетические.

В текущем прототипе SpecificationRevision хранит SourcePath/ImportProfile,
без идентичности содержимого и исходного распознанного снимка.
WorkflowChanges.SaveSpecification сравнивает параметры/цену/путь; равные
итоги при изменившейся раскладке этим пока не различаются. При реализации
нужно изменить модель источника и условие no-op, а не только добавить кнопку.
