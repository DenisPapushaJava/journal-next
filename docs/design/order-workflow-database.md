# Данные программы «Заявки»

25.10.2026. Действующий контракт после удаления истории. Он заменяет прежний
проект с `order_events`, `specification_revisions`, цепочками версий и
сравнением редакций. Новый продукт изолирован от прежнего Journal.

## Реализовано и запланировано

Реализованы локальный JSON-прототип (схема 11) и реляционный MDB-адаптер
(схема 1) через отдельный Windows x86 хост. Создание/подключение —
«Настройки → Хранилище». Нативный Jet/SMB пока не проверен на Linux;
точный контракт — [order-workflow-access.md](order-workflow-access.md).
Ориентир нагрузки: 5–10 сотрудников, до 50 новых заявок в день.
Из прежней MDB берутся только цены; её заявки, схема и настройки не меняются.

Основная модель: заявка → позиции → проекты/варианты → актуальная спецификация
и расчёт. Нет ленты действий, таблиц аудита, цепочек редакций или восстановления
прежнего расчёта. Служебная версия записи нужна для защиты параллельной работы;
она не является номером пользовательской редакции.

## Сущности Access-БД v1

| Сущность | Содержимое и ограничения |
| --- | --- |
| `employees` | Постоянный ID человека, фамилия, общий цвет. Роль технолога и доступность задаются явно; менеджер не становится технологом автоматически |
| `customers` | ID и название заказчика; имя не является первичным ключом |
| `machines` | ID, отображаемое имя, профиль импорта, расширение проекта |
| `cutting_rates` | Станок, категория, толщина, цена метра и пробивки. Одна толщина — строка, не столбец/таблица |
| `orders` | ID, деловой номер, заказчик/менеджер/ответственный, создатель, даты создания/изменения, номер БЛЦБ, корзина, служебная версия |
| `order_items` | Позиция заявки, номер, IsIncluded и ID выбранного проекта; выбранный проект принадлежит этой позиции |
| `cutting_projects` | Позиция, номер варианта, станок, толщина, имя, дата создания, путь, корзина, незавершённое переименование |
| `specifications` | Одна спецификация проекта с актуальными параметрами, сохранённым расчётом и последним принятым отчётом; ID = ID проекта |
| `accepted_reports` | Одна принятая копия на спецификацию: хеш, размер, путь и базовые поля отчёта; сами HTML/PDF вне MDB |
| `project_renames` | Единственное незавершённое переименование проекта, без ленты истории |
| `price_import_keys` | Ключи строк последнего импорта цен, без зависимости ID от масштаба decimal |
| `app_metadata` | Маркер продукта, версия схемы, ID базы, служебные версии, корень проектов и источник цен |

Расчёт и снимок тарифа хранятся в строке спецификации. Это один актуальный
расчёт, не коллекция редакций. Для MVP не требуются таблицы событий, версий
спецификации, предыдущих расчётов, маршрутов цеха или опубликованных версий
прайсов. Дальнейшие сущности добавляются после согласованного сценария.

## Идентичность, роли и локальные настройки

ID — GUID, деловые номера/фамилии/имена файлов не становятся ключами.
Скрытие роли технолога не удаляет человека или ссылки из заявок/расчётов.
Повторное явное добавление профиля использует тот же ID. Текущий профиль этого
ПК защищён от удаления. Скрытые люди остаются доступны для отображения
создателя/ответственного/автора сохранённого расчёта.

EmployeeId выбранного профиля, тема и личные подсказки менеджеров/заказчиков
хранятся локально в preferences.json. Там же путь/ID MDB и выбор технолога
для каждой базы; личный файл никогда не размещается рядом с общей MDB. Фамилия/роль/цвет человека принадлежат
данным приложения. Вход с паролем не нужен. Личные подсказки допускают свободный
ввод и не пополняются автоматически из заявок.

Разрешение введённого имени и запись реквизитов — одна операция на актуальном
снимке. Ноль совпадений — регистрация; одно — использование ID; несколько —
явная неоднозначность. Не выбирать первую строку и не делать фамилию UNIQUE
без возможности различать людей. Сравнение регистра/пробелов одинаково при
чтении и записи; для Access это требуется проверить на выбранном провайдере.

## Заявка, состав и проекты

Номер заявки — yyyy-MM-dd-HHmmss, при совпадении суффикс -02/-03; выделяется
атомарно при создании. БЛЦБ — необязательный текстовый номер, без отдельного
года. Дата документа не подменяется датой заявки или текущим временем.

При подготовке проекта вводятся только станок и толщина. Материал и категория
поступают из спецификации. Один проект — одна спецификация; другой станок
или заполненный проект другой толщины создаёт самостоятельный вариант.
Выбор варианта для итога остаётся явным действием.

IsIncluded относится к позиции и её вариантам. Исключённая позиция сохраняет
проект/расчёт, но не входит в итог/письмо/комплектность. Корзина заявки и
корзина проекта — отдельные признаки deleted_at/deleted_by; восстановление
возвращает тот же объект. Физические рабочие папки при этом не удаляются.

Для пустой заготовки разрешено изменить станок/толщину с переименованием
папки и файла, сохраняя ID/исходное время. Намерение Rename необходимо для
восстановления после частичной файловой операции. Это текущее служебное
состояние, а не история действий. Файловые операции выполняются вне транзакции
БД, конфликтующие пути не перезаписываются; блокировка показывается понятно.

## Актуальная спецификация и цена

В текущем состоянии сохраняются номер/дата документа, станок и материал,
категория, толщина/размер заготовки, количество, длина в метрах, пробивки,
вес, время, ручной коэффициент, независимые гибка и фаска (HasChamfer,
по умолчанию false), комментарий, время и автор сохранения.
Станок/толщина соответствуют подготовленному проекту. Непроверенный материал
нельзя подтвердить фокусом или автоподсказкой.

Формула:

`(метры × цена метра + пробивки × цена пробивки) × ручной коэффициент`.

В расчёте хранятся сами цены, составляющие и итог, а не только ссылка на прайс.
Изменение общего тарифа не меняет сохранённый расчёт. Обновление тарифа явно;
после сохранения прежнее состояние заменяется новым. Нет скрытого минимального
платежа или дополнительного округления. Расчёт выполняется единым decimal-
расчётчиком, не повторяется независимо в SQL и UI. Гибка — отдельно, цена
не определена. Пробивки/длина отчёта уже являются итогами: не умножать их
повторно на число листов. Отсутствующий расчёт не равен цене 0.

## Последний принятый отчёт

Для обновления нужен только актуальный расчёт и исходные распознанные значения
последнего принятого HTML/PDF. Их сравнение с новым отчётом позволяет сохранить
ручные исправления либо запросить выбор спорного поля. Полная хронология
редакций для этого не нужна.

Принятый отчёт содержит имя, размер, SHA-256, путь к сохранённой копии и базовые
распознанные поля. Сейчас копия находится в .workflow-reports/<hash>/<имя>
рядом с проектом. Изменение байтов обнаруживается и при прежних mtime/размере;
те же байты не создают повторное состояние. Открытие принятой спецификации
проверяет целостность копии. В JSON/Access не помещаются сами PDF/CAM-файлы.

После обновления спецификация ссылается на последний принятый отчёт. Старые
служебные копии файлов не удаляются миграцией; очистка файлов требует своего
согласованного правила. Рабочие CAM/HTML/PDF остаются на прежних местах.

## Ограничения и индексы

PK всех сущностей, FK владельцев и пользователей, обязательные поля и UNIQUE
задаются в файле БД. Поддержку конкретных ограничений Jet/ACE проверяют нативно.
Без каскадного удаления справочников с рабочими ссылками.

Минимальные ключи: orders(reference_number) UNIQUE;
order_items(order_id, item_no) UNIQUE; cutting_projects(order_item_id, variant_no)
UNIQUE; одна спецификация проекта; cutting_rates(machine_id, material_group,
thickness_mm) UNIQUE. Выбранный проект должен принадлежать своей позиции.

Кандидаты индексов: orders(created_at, id), orders(technologist_id, created_at,
id), orders(deleted_at, id), orders(blcb_number); индексы FK дочерних таблиц.
Номер БЛЦБ не UNIQUE. Дополнительные индексы вводятся по реальным запросам
и замерам, не по каждому отображаемому столбцу. Проект запросов —
[order-workflow-queries.md](order-workflow-queries.md).

## Запись, миграция и границы проверки

Текущий JSON store использует короткую файловую аренду и условную запись,
атомарную замену файла и no-op без увеличения версии. Это локальный прототип,
не сетевое хранилище. MDB читает ограниченные страницы и ID, без загрузки
всех заявок. Транзакция одного соединения: служебный токен metadata →
заявка → дочерние записи по ID; никакой транзакции на время формы,
диалога, парсинга или копирования файлов.

Неизвестный исход записи сверяется по устойчивым ID/служебным версиям;
автоматический повтор записи запрещён. Служебные данные восстановления и
диагностика ошибок не являются пользовательской историей.

JSON 1–10 → 11: исходные байты копируются перед записью, из цепочки берётся
последнее состояние, события отбрасываются. До этого восстанавливаются
создатель/роли из старых данных. ID/номера/служебные версии/цены/последний
отчёт/корзина/варианты сохраняются. Повторное чтение не переписывает файл.
Невалидный источник не заменяется. Старый Journal и его MDB не затрагиваются.
Нативные Windows/SMB/Jet остаются обязательной проверкой перед выпуском.
Windows lifecycle-тест добавлен; пропуск Linux не подтверждает DDL/блокировки.
