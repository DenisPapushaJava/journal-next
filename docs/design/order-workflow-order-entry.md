# Новая заявка и списки менеджеров/заказчиков

24.10.2026. Реализовано в локальном Avalonia-прототипе feature/order-workflow,
без коммитов/PR/релиза. Прежний Journal не изменяется. Схема workspace остаётся 7;
общий Access-адаптер ещё не реализован.

## Форма и авторство

Новая заявка содержит два редактируемых поля: менеджер и заказчик. Технолог
не вводится: в момент сохранения текущий EmployeeId сеанса становится автором
создания и начальным ответственным технологом. Смена профиля после открытия
формы учитывается. Пустой профиль блокирует запись; CreatedById существующих
заявок не меняется.

Форма выровнена слева в правой панели, ширина 600 px с внутренними отступами
20 px; менеджер — 320 px, заказчик — оставшаяся ширина около 560 px. Минимальная
ширина правой панели уже ограничена 760 px. Начальный фокус на менеджере,
затем заказчик, кнопки «Создать»/«Отмена» в пределах формы.

Используется существующий EntrySuggestionComboBox прежнего Journal, без
изменения его кода: весь список по стрелке/F4/Alt+↓, локальный поиск с начала
без учёта регистра, SuggestAppend с выделенным продолжением. Enter принимает
вариант без сохранения заявки, Tab принимает и переходит дальше, Esc убирает
продолжение/закрывает список. Свободный ввод разрешён. Фокус, импорт списка и
смена источника подсказок не подставляют значение за пользователя. Запросов
БД на букву и новых таймеров нет.

## Личные списки

Последнее решение пользователя: подсказки менеджеров и заказчиков локальны
на каждом рабочем месте, как в прежнем Journal. Предложенный ранее общий
источник подсказок отклонён. Общий сотрудник/его цвет остаются в БД; это
другое назначение данных. Локальный выбор EmployeeId и тема сохраняются.

«Настройки → Общие → Данные для выпадающих списков» открывает отдельное
модальное окно с двумя колонками, по значению на строку. Самостоятельного
раздела списков в левой навигации нет.
Пустые списки допустимы и сохраняются пустыми после перезапуска. Никакого
автоматического пополнения из истории: создание заявки со свободным именем
не добавляет подсказку. Материал сюда не включён: он поступает из отчёта.
Редактирование списка не переименовывает/удаляет сотрудников, заказчиков и
исторические заявки.

Данные находятся в preferences.json отдельного профиля JournalWorkflow:
Windows — LocalApplicationData/JournalWorkflow, Linux — ApplicationData/JournalWorkflow.
Это профиль пользователя ОС; коллеги и другое рабочее место имеют свои списки.
Перенос старых настроек/заявок автоматически не выполняется.

Нормализация использует прежний EntrySuggestions: обрезка краёв, удаление
пустых строк и дублей без учёта регистра с сохранением первого написания и
порядка. До 200 значений в каждом списке, имя до 255 символов без управляющих
символов, суммарно до 16000 символов. Максимальный размер preferences.json
увеличен с 8 до 128 KiB; проверка размера выполняется также до фиксации записи.

Списки сохраняются своей кнопкой «Сохранить»; успешная запись закрывает окно,
«Отмена»/Esc закрывают без записи. После закрытия фокус возвращается к кнопке
открытия, счётчики подсказок обновляются. Во время записи закрытие блокируется.
Несохранённые профиль/папка остаются в родительских настройках без применения. Тема/выбор сотрудника обновляют только
свои поля предпочтений. Списки сравниваются с исходным снимком под файловой
блокировкой: чужое отличие возвращает конфликт и оставляет ввод. Повтор уже
сохранённого результата — no-op. Ошибка доступа/JSON/валидации сохраняет
прежний файл и ввод редактора; нет скрытого повтора записи.

## Создание заявки и конкурентный доступ

Выбранные значения менеджера/заказчика сохраняются в самой заявке через
постоянные ID. Отсутствие в личных подсказках не запрещает свободное имя.
CreateOrderFromNamesAsync читает актуальный workspace под одной блокировкой,
разрешает оба имени, регистрирует отсутствующие сущности, выделяет номер и
создаёт заявку одной атомарной заменой файла. Глобальная версия старого
снимка формы не требуется: изменения других заявок не затираются.

Имена обрезаются и проверяются. Одно точное совпадение без учёта регистра
использует существующий ID; несколько совпадений отклоняются с просьбой
уточнить имя/название. Выбора случайной первой записи и автоматического
склеивания одноимённых сущностей нет. Полноценный выбор одноимённых сущностей
по ID остаётся задачей будущего общего адаптера. Если проверка автора или
другого поля не прошла, новый менеджер также не записывается.

Текущие операции не держат одновременно workspace.lock и preferences.json.lock.
Сохранение профиля завершает запись workspace до обращения к preferences.
Создание заявки не читает личный файл подсказок; сохранение подсказок не читает
workspace. FileShare.None даёт немедленный отказ при занятости, без ожидания
чужого освобождения и без .Wait/.Result на UI. Локальный тест двух клиентов
проверяет целостность и ограниченный срок завершения; при подтверждённом
отказе допускается явное повторное действие пользователя.

Это устраняет цикл ожидания между этими двумя файлами в проверенных сценариях,
но не обещает отсутствие блокировок будущей Access на SMB. Подробности её
порядка записи и риска одновременной регистрации имён —
[проект запросов](order-workflow-queries.md#сохранение-и-блокировки).

## Проверка

Проверены обе темы, главный экран 1366/1180×768, настройки 900×660/800×580
и отдельный редактор списков 800×560/680×440:
размеры/фокус, SuggestAppend, Enter/Tab/Esc/F4, свободный ввод, применение
изменённых подсказок без сброса текста. Проверены перезапуск/изоляция профилей,
пустые списки, большие кириллические списки, некорректный ввод/JSON, конфликт
двух редакторов, независимость двух файловых блокировок, актуальный автор,
атомарность, одинаковые имена и номера при конкурирующем создании.

113 Workflow-тестов: 110 успешны, 3 необязательных пропущены. Release-сборка
без предупреждений/ошибок. Итоговый лог: .local/workflow-settings-program-tests.log, сборка:
.local/workflow-settings-program-build.log, скриншоты: .local/workflow-settings-program-ui/.
Headless-проверки не заменяют нативный ввод Windows и испытания Jet/ACE/SMB.
