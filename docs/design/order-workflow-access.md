# Общая MDB Journal Next

Этап реализации 25.10.2026. Только новый продукт; прежняя MDB — источник цен.
Сохранённый путь не создаёт базу автоматически. «Создать БД…» создаёт новый
файл, «Подключить БД…» проверяет существующий. Рабочий источник применяется
после успешного чтения/проверки и сохранения локальных настроек.

## Контракт хранилища и Windows-хоста

`IWorkflowWorkspaceStore` отделяет UI от JSON. JSON остаётся средой разработки
Linux и не размещается на SMB. MDB обслуживает x86 AccessHost отдельным
`--workflow` протоколом 1; прежние операции Orders не принимают новую схему.
Никакого HTTP/сервера на компьютере-хранилище не требуется.

Операции: Create, Inspect, Read (период/поиск/страница и нужные открытые ID), ReadOrders
(конкретные ID), ReadTrash, Apply, Purge и ReadRevision (только metadata). Запросы/ответы типизированы, SQL от UI не
принимается. Apply содержит ожидаемые версии и изменённые сущности; подтверждён
только валидный полный ответ после завершения хоста. Обрыв после отправки записи
означает неизвестный исход: F5/сверка ID, без автоматического повтора.

Создание: ADOX/Jet 4 в x86, временная MDB в выбранной папке, DDL/индексы/FK,
пустые данные и штатные станки, проверка схемы, закрытие соединений, Move без
перезаписи. В metadata — ProductId, SchemaVersion, уникальный DatabaseId.
Обычное подключение/чтение не выполняет DDL и не меняет исходный файл.

Схема реляционная: сотрудники, заказчики, станки, тарифы, заявки, позиции,
проекты, актуальные спецификации/расчёты, принятый отчёт и rename intent.
Нет JSON-поля со всем workspace, истории событий или бинарных HTML/PDF в MDB.
GUID — ключи; денежные/расчётные поля decimal, даты UTC, индексы FK и рабочих
периодов/номеров. Выбранный проект принадлежит своей позиции; циклическая связь
устанавливается внутри транзакции после вставки проекта.

Запись: короткая транзакция, общий служебный токен изменения, затем заявка и
дочерние строки в определённом порядке. Токен сериализует только короткие записи
для текущей небольшой команды; исходная metadata читается до начала TX
(без повышения двух общих блокировок); разбор/копирование отчёта, диалоги, сеть вне SQL
и ожидание ввода никогда не держат транзакцию. No-op не пишет. Меняются только
отличающиеся строки; исходная версия заявки и каталога проверяются до фиксации.

Чтение журнала ограничено периодом/поиском и страницей, открытые карточки
читаются по ID отдельно. Страница 100, максимум 200, стабильный курсор updated_at +
order_number. Дочерние строки читаются группами ID до 75; тарифы передаются
только при изменении catalog_revision. До/после группы чтений сверяется revision;
при изменении снимок отклоняется. После Inspect/Read/ReadOrders/ReadTrash клиент
проверяет ID/revision/catalog_revision через ReadRevision в свежем x86-процессе:
это исключает старый кэш Jet при заключительной проверке, без загрузки каталога
и заявок второй раз. На оба чтения общий срок 45 секунд, отмена/ошибка не
применяют снимок. Записи не повторяются и не требуют этой дополнительной сверки:
ответ подготовлен под их собственным write token. No-op читает ответ под тем
же токеном до rollback. Jet поддерживает ReadCommitted; Page Timeout/User Commit
Sync — свойства сессии, их нельзя передавать в строке OleDb/ADOX. Используются
штатные параметры провайдера. Поиск — 300 мс/Enter сразу, отмена/
поколения ответов, до 8 слов (лимит числа параметров Jet); SQL получает только
параметры. Любая подстрока не обещает index seek. Нельзя перенести чтение всего
JSON-workspace на всю MDB.
DECIMAL(28,10): до 18 целых и 10 дробных знаков; лишняя точность отклоняется
с сообщением, без молчаливого округления. Nullable/пустые строки различаются.
Флаг backupBeforeWrite относится к локальному JSON; MDB не копируется целиком
во время общей работы, атомарность записи обеспечивается транзакцией.

Purge — отдельная условная операция для корзины: весь подтверждённый набор
ID/версий проверяется до удаления, затем удаляются дочерние строки и заявки
одной транзакцией (до 10 000 ID, параметры группами по 75). Расчёты не
передаются клиенту для удаления. При ошибке версии не удаляется ничего;
после неизвестного исхода нужен F5 или явное обновление корзины, без повтора.
Письма после restart сначала читаются по ID вне стартового периода; локальный
черновик удаляется только после успешного восстановления и если его не заменил
более новый.

Личные настройки/списки/письмо — локально; выбранный технолог привязан к ID БД.
Новая база не получает тестовые фамилии или заявки, цены импортируются явно.

После ревью 25.10.2026 активное подключение и EmployeeId — одно состояние
сеанса. Если другой экземпляр выбрал другую базу в preferences, F5 сообщает
о смене, сохраняя текущий источник и ввод. Сохранение профиля сравнивается
с активным источником до записи в MDB и при условной записи preferences.
Явное подключение к уже выбранной другим экземпляром базе сохраняет отдельный
выбор сотрудника прежнего источника.

Курсор привязан к фильтру (период, поиск, размер страницы). Смена фильтра сразу
сбрасывает курсор/счётчики; RetainIds не меняет фильтр. Поздний ответ не может
восстановить продолжение прежнего поиска. При смене catalog_revision новый
каталог и полученные заявки валидируются до замены кэша. Если старые cached
orders ссылаются на исчезнувшие записи каталога, только эти ID перечитываются
порциями до 512: удалённые исключаются, существующие заменяются свежими.
Изменение каталога во время сверки отклоняет её, ошибка оставляет прежний
согласованный кэш. Локальные черновики живут отдельно и не теряются.
Неудача применения ответа уже выполненного Apply/Purge блокирует запись до
F5/сверки, как обрыв ответа; новую запись автоматически не отправлять.

## Проверка

После исправлений ревью: 308 успешных .NET-проверок, 4 пропуска (312 всего),
5 Python-проверок; locked restore, Debug/Release и Windows-путь подготовки
self-contained x86 хоста без предупреждений/ошибок. Win-x64/x86 также
собирались на предыдущем этапе MDB.
Управляемые сценарии включают 601 ID корзины/конфликт/неизвестный исход,
поздний поиск, восстановление писем вне стартового периода и обе темы Storage.
13 новых регрессий проверяют источник/профиль, курсор/поздний ответ,
переименование/UTC/точность Jet, частичный кэш и отказ повтора записи.
Снимки и логи находятся в .local/workflow-mdb-* / .local/review-fixes-*.

Создание/DDL/Jet требуют отдельного нативного Windows x86 прогона. Linux может
проверить модели, SQL/параметры, протокол/ошибки, условные записи и UI через
управляемые тестовые реализации; это не подтверждает работу Jet/SMB.

## Проверка на Windows перед выпуском

Обычная сборка Desktop на Windows подготавливает self-contained AccessHost x86
в bin/<Configuration>/net10.0/AccessHost. Нативный тест WorkflowNativeMdbTests
находит Release-хост; можно явно задать WORKFLOW_TEST_ACCESS_HOST. В Windows CI
он запускается общим dotnet test (не пропускается из-за отсутствия env).
Проверяются создание/полная структура, запрет перезаписи, профиль/заявка/проект/
переименование реальной папки/файла после UTC с сохранением времени имени,
сохранённый тариф/расчёт, поиск, корзина/окончательное удаление и чужой ID базы. На Linux тест
явно пропущен. Отдельно нужны реальная SMB-папка, права/обрывы и два компьютера.
Локальная публикация x86 host в .local — сборочная проверка, не релиз.

Основание параметров провайдера: [Microsoft Jet OLE DB provider](https://learn.microsoft.com/en-us/office/client-developer/access/desktop-database-reference/microsoft-ole-db-provider-for-microsoft-jet).
