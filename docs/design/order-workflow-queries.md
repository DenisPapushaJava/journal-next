# Запросы, индексы и проверка новой БД Workflow

24.10.2026, корзина: Q1 рабочего списка исключает deleted_at IS NOT NULL.
Обычные записи дополнительно проверяют deleted_at IS NULL; восстановление —
отдельную ожидаемую версию удалённой заявки. Корзина читается порциями по
(deleted_at DESC, registration_no DESC), с именем удалившего через employees
и без чтения всех версий/файлов. Индекс не должен игнорировать null-ключи,
если его используют также для активной области. Нет каскадного удаления
проектов/расчётов и повторного выделения номера при восстановлении.

24.10.2026, полоса автора: Q1 получает orders.created_by, имя и общий цвет
автора одним LEFT JOIN employees по PK. Отдельного чтения сотрудника на
каждую строку/при наведении нет, основной курсор прежний. В нынешнем локальном
JSON-прототипе эти данные уже загружены, автор берётся из первого события
создания. SQL ниже остаётся проектом будущего Access-адаптера.

24.10.2026, подтверждённое деловое обозначение заявки — reference_number
(yyyy-MM-dd-HHmmss[-02]), отдельное от внутреннего registration_no. Q1
возвращает его для интерфейса, курсор и стабильный порядок прежние. Точный
поиск по полному номеру использует UNIQUE-индекс reference_number; выбор
кандидатов одного временного префикса также должен идти по индексу. Полная
загрузка всех номеров при создании допустима только в нынешнем локальном
JSON-прототипе, где весь workspace уже прочитан; в общий Access её не переносить.

24.10.2026. Дополнение к [модели](order-workflow-database.md). Это проект
общего адаптера, не устройство нынешнего LocalWorkflowWorkspaceStore.
Нагрузка пользователя: 5–10 сотрудников в день, до 50 заявок в день.
Тестовый запас — 10 одновременно работающих клиентов. Пользователь выбрал
общий файл Access. Домашняя работа отложена. Конкретный формат
MDB/ACCDB и провайдер ещё предстоит проверить. SQL ниже — проект Access SQL,
не выполненная миграция и не проверенный Jet-прогон.
Результаты производительности этим документом не заявляются.

Уточнение сценария 24.10.2026: [подготовка и переделка проектов](order-workflow-project-preparation.md)
предшествует расчёту. Подтверждено: один проект — одна спецификация, возможна
переделка под другой станок. Предложение — order_items с current_project_id,
варианты cutting_projects, одна specifications на вариант и её версии.
В итог Q2/Q3 попадает только выбранный вариант позиции. Старые варианты
читаются отдельно и не увеличивают цену/число позиций. Этот слой и подписи
счётчиков ещё обсуждаются; SQL и индексы — проект до проверки Access DDL.

## 1. Что считаем эффективностью

- Запрос получает данные нужного экрана, без всей истории и содержимого файлов.
- Число SQL-запросов/сетевых обменов не растёт по одному на каждую строку.
- Первая порция небольшая; последующие загружаются по обращению.
- Запись краткая, атомарная, с проверкой версии изменяемой сущности.
- Семантика поиска/фильтров/сумм сохраняется при оптимизации.
- Индекс подтверждается планом и измерением, не предположением по названию поля.

Первый вариант порции списка — 100, верхний предел — 200 записей. Это
параметры проекта, не согласованное ограничение числа заявок/спецификаций.
Число спецификаций в заявке не ограничивается размером порции экрана.

Не вводим заранее отдельные БД чтения/записи, секционирование, репликацию,
Elasticsearch, полное кеширование архива и хранимые итоги. Кеши справочников/
конкретной версии прайса допустимы; у них известен ID/версия и путь обновления.

## 2. Каталог основных чтений

Для [подбора отчётов](order-workflow-specification-refresh.md) предлагаются
Q11 (папки/источники вариантов одной заявки) и Q12 (базовые снимки только
кандидатов). Поиск ограничен соседними файлами проектов. Равенство mtime/
размера не позволяет пропустить проверку байтов при явном обновлении.
Отсутствующие/нечитаемые отчёты не превращаются в нули или удаление данных.
Пакетное применение выбранных готовых редакций — одна защищённая транзакция.

| Код | Сценарий | Результат и ограничение |
| --- | --- | --- |
| Q1 | Журнал по периоду/технологу | Порция кратких реквизитов, ID, content_version; без версий и событий |
| Q2 | Итоги порции Q1 | Числа позиций/расчётов выбранных вариантов и суммы только выбранных ID |
| Q3 | Карточка заявки | Порция позиций с выбранным проектом/спецификацией/расчётом; история вариантов отдельно |
| Q4 | История спецификации | Порция кратких версий по revision_no, без всех файлов/работ |
| Q5 | Сравнение | Два конкретных ID одной спецификации, детали этих версий |
| Q6 | События заявки | Порция по occurred_at + id; не весь event log |
| Q7 | Тариф | Одна строка по опубликованной версии/категории/толщине |
| Q8 | Поиск по текущим спецификациям | Уникальные заявки через EXISTS; фильтры до ограничения порции |
| Q9 | Справочник/прайс | Нужный небольшой каталог либо порция тарифа, ID/версия снимка |
| Q10 | Проверка записи | Квитанция по command_id + проверка actor/kind/hash |

Q1/Q2 выполняются одной короткой операцией хоста с проверкой согласованности
по content_version и составу порции. Q3 тоже проверяет целостность набора,
не держит транзакцию на время работы формы. История/события читаются отдельно при открытии соответствующей области.
Большая заявка не заставляет открытие карточки вычитать весь архив версий.
Дополнительные сведения получаются ограниченными наборами типизированных
ID, без N+1. SQL-массива и unnest в Access нет.

## 3. Список и порционная загрузка

Предложение стандартного порядка — registered_on DESC, registration_no DESC.
День регистрации ещё требует согласования; SQL показывает эту предложенную
семантику. Уникальный registration_no делает порядок однозначным. UUID при
других сортировках служит дополнительным ключом равных значений.

Следующая порция использует значения последней строки, без вычитывания
всего архива. Условие составного курсора раскрывается через сравнения/OR.
Первый и следующий запросы — разные параметризованные формы.
TOP выбирается из разрешённых приложением размеров, не из сырого ввода.
Однозначный ORDER BY нужен также из-за поведения Access TOP на равных ключах.

~~~sql
PARAMETERS pFrom DateTime, pTo DateTime,
           pCursorDay DateTime, pCursorNo Long;
SELECT TOP 100 o.id, o.registration_no, o.reference_number, o.registered_on,
       o.customer_id, o.manager_employee_id, o.technologist_employee_id,
       o.blcb_number, o.blcb_year, o.content_version, o.updated_at,
       o.created_by, author_employee.display_name AS creator_name,
       author_employee.color_argb AS creator_color
FROM orders AS o LEFT JOIN employees AS author_employee
  ON o.created_by = author_employee.id
WHERE o.archived_at IS NULL
  AND o.deleted_at IS NULL
  AND o.registered_on >= [pFrom]
  AND o.registered_on < [pTo]
  AND (o.registered_on < [pCursorDay]
       OR (o.registered_on = [pCursorDay]
           AND o.registration_no < [pCursorNo]))
ORDER BY o.registered_on DESC, o.registration_no DESC;
~~~

pCursorNo Long здесь соответствует кандидату MDB/32-bit; если физический
тип будет иным, меняется и объявление параметра. В OleDb параметры
привязываются в порядке провайдера, типы задаются явно. Имена в QueryDef
не заменяют проверку реального OleDb-порядка. Первая порция не имеет
параметров/условия курсора. Все даты и GUID передаются типизированно.

Имена заказчика/сотрудников можно получить JOIN-ами по PK в том же запросе;
это связи к одной строке, без размножения результата. Вариант «Мои» добавляет
равенство technologist_employee_id; вариант по заказчику — customer_id.
Не включать все необязательные фильтры через OR в один универсальный SQL:
используется небольшой набор составляемых форм с типизированными параметрами
и разрешёнными полями/направлениями сортировки, без SQL из пользовательского текста.

При смене фильтра/порядка курсор сбрасывается. Курсор принадлежит конкретному
запросу, не переносится между разными отборами. Пользовательская сортировка
с NULL имеет явный порядок NULL и соответствующий составной курсор.
Внутри одной порции согласованность подтверждается проверкой версии и состава;
между порциями
новые записи/смена условий могут менять набор. После обновления перечитывается
актуальная порция, выбор хранится по ID. Seek не обещает замороженный на
минуты список; при необходимости стабильного экспорта нужен отдельный сценарий.

Для timestamp-периода границы дня вычисляются в часовом поясе организации,
передаются как UTC [from, to). Не оборачивать индексируемую колонку в
DATE(timestamp)/форматирование ради фильтра; исходная дата документа остаётся
отдельной. Поиск по дате документа проходит через текущую версию спецификации.

## 4. Итоги без размножения строк

Q2 получает только ID из Q1. В Access для этого используются типизированные
параметры IN с ограничением размера запроса; большие порции делятся на
фиксированное число блоков. Ни SQL-массивов, ни общей staging-таблицы с DDL
на каждое чтение не требуется. Пример блока из трёх ID:

~~~sql
PARAMETERS pId1 Guid, pId2 Guid, pId3 Guid;
SELECT i.order_id,
       COUNT(i.id) AS item_count,
       COUNT(c.revision_id) AS calculated_count,
       SUM(c.payable_total) AS known_cutting_total
FROM ((order_items AS i
LEFT JOIN cutting_projects AS p ON p.id = i.current_project_id)
LEFT JOIN specifications AS s ON s.id = p.id)
LEFT JOIN cutting_calculations AS c ON c.revision_id = s.current_revision_id
WHERE i.archived_at IS NULL
  AND i.order_id IN ([pId1], [pId2], [pId3])
GROUP BY i.order_id;
~~~

Объявление Guid проверяется с выбранным провайдером/DDL. Предел числа
параметров и длины SQL проверяется на Access; это не произвольный IN
с текстовой подстановкой GUID. Для заявки без позиций строки Q2 нет:
адаптер сопоставляет результат с Q1 и возвращает counts=0, сумму NULL.
Повторяющихся ID в запросе не должно быть.

NULL суммы сохраняется, если расчётов нет. При наличии части расчётов сумма
явно частичная. Базовая полнота требует item_count > 0 и расчёта каждого
выбранного варианта. Незавершённая переделка при старом выбранном варианте
показывается отдельно; её влияние на подтверждение итога ещё обсуждается. RUB/совместимость валют закрепляется первым DDL;
суммы разных валют не складываются.

Работы, события и файлы не JOIN-ятся в эту агрегацию: связи 1:N размножили бы
цену одной спецификации. Бейджи работ получают через EXISTS/отдельную
агрегацию до JOIN. Новая цена прайса не участвует в Q2: используется
сохранённый расчёт текущей версии.

Хранимый order_summary добавляется только если Q2 измеренно дорог.
Тогда он поддерживается той же транзакцией, проверяется пересчётом и
не редактируется UI. Сначала измеряем запросы на настоящем файле.

## 5. Поиск и смысл фильтров

Уточнение имён: искать/показывать исходное привычное имя CAM-проекта
и номер отчёта отдельно от внутреннего номера позиции/варианта. Общее
имя не доказывает принадлежность: неоднозначные совпадения показывают
заявку/заказчика/станок/вариант. Для частого точного поиска имени оценивается
неуникальный индекс, не принудительное переименование файлов.

Базовый список работает с выбранным вариантом каждой позиции и текущей
версией его спецификации. Старый материал другого варианта/версии не
включает заявку в фильтр текущего материала. Поиск по истории — отдельный будущий
режим, если понадобится.

Предложение нескольких фильтров спецификации: одна текущая спецификация
удовлетворяет всем ограничениям материала/толщины/станка. Это нужно закрепить
в UX, иначе лазер + Ст3 могло бы означать две разные спецификации.

Ограничения задаются через EXISTS по order_items/current_project_id,
его спецификации/current_revision_id до TOP. Для Access проверяются коррелированный EXISTS, скобки JOIN и
порядок параметров на синтетическом файле. При дорогом плане сравнивается
эквивалентная выборка уникальных ID; смысл фильтра остаётся тем же.
Отбор уже ограниченной страницы в памяти не является глобальным поиском.
Связи с работами/файлами не размножают строки заявок.

Поисковые значения имеют отдельный контракт нормализации: крайние пробелы,
регистр, Unicode. Ведущие нули, внутренние пробелы и знаки не теряются;
ё/е не объединяются без правила. Нормализованное поле или expression index
должны точно соответствовать выражению запроса и collation.

Точный поиск, префикс и подстрока — разные операции. Обычный B-tree не
объявляется ускорителем произвольной подстроки. Для Access проверяется
режим LIKE выбранного OleDb/QueryDef: символы %/_ и */? нельзя смешивать
как эквивалентные без проверки ANSI-режима. Символы пользователя экранируются.
Поиск подстроки измеряется отдельно, гарантия index seek для него не даётся.
Внешняя поисковая служба/pg_trgm не входят в выбранный файловый подход.
Короткие строки не запрещаются молча ради индекса. Отдельную копию всех
текущих поисковых данных вводить только после измерений, с атомарным
обновлением при смене текущей версии и проверкой восстановления.

В БД ввод поиска отправляется с отменой/проверкой поколения; поздний ответ
не заменяет актуальный. Предпросмотр цены использует загруженную конкретную
версию прайса и не выполняет SQL на каждую цифру длины/коэффициента.

## 6. Индексы: обязательные ограничения и кандидаты

PK и UNIQUE из модели обеспечивают целостность независимо от оптимизации.
Не дублировать их автоматически отдельными индексами на те же колонки.

| Чтение | Кандидат B-tree | Замечание |
| --- | --- | --- |
| Q1 период | orders(registered_on DESC, registration_no DESC) | Обычный индекс; archived_at/deleted_at проверяются дополнительно |
| Корзина | orders(deleted_at DESC, registration_no DESC) | Порции по стабильному курсору; чтение deleted_at IS NOT NULL |
| Q1 «Мои» | orders(technologist_employee_id, registered_on DESC, registration_no DESC) | Равенство сотрудника перед диапазоном/порядком |
| Q1 заказчик/менеджер | Соответствующий ID, registered_on, registration_no | Добавлять при частом отборе и подтверждённом выигрыше |
| Номер заявки | orders(reference_number) | UNIQUE; точный поиск/защита совпадений, номер yyyy-MM-dd-HHmmss[-02] |
| БЛЦБ | orders(blcb_number, blcb_year) | Не UNIQUE; отдельная нормализация при регистронезависимом поиске |
| Q2/Q3 | order_items(order_id, position) | UNIQUE порядка; отдельный UNIQUE неизменяемого item_no |
| История вариантов | cutting_projects(order_item_id, variant_no) | UNIQUE; выбранный вариант читается по current_project_id |
| Спецификация варианта | specifications(id) | Предлагаемый PK/FK проектного ID |
| Q4 | specification_revisions(specification_id, revision_no) | Уже UNIQUE, годится для чтения назад |
| Q5 | specification_revisions(id) | PK, точечное чтение |
| Q6 | order_events(order_id, occurred_at DESC, id DESC) | Однозначная порционная история |
| Q7 | cutting_rates(price_list_version_id, material_group_id, thickness_mm) | Уже UNIQUE |
| Работы | revision_operations(revision_id, position) | Уже UNIQUE |
| Файлы версии/заявки | revision_files(revision_id, file_id), order_files(order_id, file_id) | UNIQUE связи с нужным ведущим владельцем |
| Q10 | command_receipts(command_id) | PK, не сканировать историю событий |

Составные UNIQUE для FK принадлежности сохраняются, даже если глобальный
PK ID тоже уникален: они защищают именно владельца ссылки. Нужные индексы
ссылающихся колонок проверяются отдельно, включая запросы удаления/проверки
FK. Проверяются реально созданные индексы Access, чтобы не дублировать
автоматические индексы отношений. Не индексируем каждое булево поле отдельно.
Partial indexes, GIN, INCLUDE и PostgreSQL-выражения не предполагаются.
Индексы ограничены возможностями/лимитами Access; размер учитывается вместе
с таблицами в бюджете файла.

## 7. Сохранение, блокировки и согласованность Access

Команда получает command_id, actor, версии затрагиваемых сущностей и ввод.
Форма не держит соединение/транзакцию; парсинг, диалоги и копирование файлов
выполняются вне транзакции. Полностью неизменённая форма — no-op без записи.

После включения вариантов этот алгоритм относится к конкретному проекту/
спецификации. Создание варианта и переключение current_project_id — отдельные
команды под версией позиции; принадлежность варианта проверяется составным FK.
Внутри варианта станок фиксирован: другой станок требует нового варианта,
не незаметной смены машины исторического проекта. Алгоритм ещё не реализован.

Кандидат алгоритма сохранения спецификации:
1. Начать транзакцию одного соединения Access. Зарезервировать command_id;
   уникальность не позволяет второй записи с тем же ID. Проверить
   actor/kind/payload_hash, если команда уже зафиксирована.
2. В транзакции выполнить условный UPDATE строки заявки с проверкой
   archived_at IS NULL / deleted_at IS NULL и увеличением content_version. Это получает блокировку
   родителя на время записи; проверяется число затронутых строк.
   Не использовать PostgreSQL SELECT FOR UPDATE.
3. Перечитать спецификацию, сверить её row_version/current_revision_id.
   CAS общих реквизитов заявки не включается в эту проверку.
4. Проверить тариф, материал, геометрию и работы. Вставить новую версию,
   детали, расчёт, работы, связи файлов, событие. Переключить текущую
   версию условным UPDATE с ожидаемой версией, увеличить row_version.
5. Сохранить результат command_receipts и commit. При любой ошибке до commit —
   rollback всей операции, включая увеличение content_version родителя.

Новое добавление, архивирование и правка метаданных используют тот же порядок
получения блокировки заявки. Общие поля проверяют orders.row_version.
Порядок: квитанция → заявка → спецификации по ID. Набор прайсов блокируется
в постоянном порядке ID, без одновременного удержания заявок.

Это проект алгоритма: транзакционность DML, реальное получение/освобождение
блокировок и affected rows должны быть доказаны Windows/Jet либо ACE тестами.
Access может блокировать страницы и вызывать занятость соседних записей:
логическая независимость двух заявок не обещает отсутствия ожидания.
Не применять глобальный lock всей БД или удержание формы под транзакцией.
При подтверждённой занятости — ограниченный срок ожидания с понятной причиной;
неподтверждённую запись/commit автоматически не повторять.

После обрыва исход неизвестен. Черновик/command_id сохраняются; Q10 проверяет
квитанцию и фактические записи. Отсутствие квитанции до завершения операции
не доказывает откат. Повторный ID с другим составом отклоняется; явная
повторная отправка после сверки использует тот же ID/состав. F5 с узким
фильтром не доказывает отсутствие созданной заявки.

### Создание заявки и свободные имена

Личные подсказки менеджеров/заказчиков не являются общими справочниками.
Они читаются локально, без SQL при наборе. Сохранение новой заявки получает
проверенный actor_id активного профиля и два имени. Имена нормализуются
одинаково при записи и поиске; конкретная collation Access должна совпасть
с проверенной политикой сравнения, а не предполагаться эквивалентной .NET.

Кандидаты employees/customers выбираются индексированным равенством по
нормализованному имени, с пределом 2: ноль — регистрация, один — существующий
ID, несколько — неоднозначность без склейки/выбора первой строки. Название
не становится UNIQUE-ключом: разные люди/заказчики могут называться одинаково.
Для таких сущностей будущему UI нужен явный выбор ID с различимыми подписями.
Полную загрузку справочников/номеров из локального JSON в Access не переносить.

Наивная последовательность SELECT «нет имени» → INSERT создаёт гонку:
два клиента могут оба увидеть отсутствие. Текущая реализация защищена одним
локальным workspace.lock; это не доказательство для общего файла Access.
Кандидат для адаптера — заранее созданная отдельная строка координации
регистрации справочников. Только команды, способные создать сотрудника/
заказчика, условно изменяют её в короткой транзакции и повторно разрешают
имя до INSERT. Сохранение профиля при регистрации сотрудника использует тот
же порядок. Это сериализация редкой регистрации, не общий mutex всех
заявок/клиентов; обычное чтение подсказок/заявок её не использует.

Предлагаемый порядок для такой команды: квитанция command_id → координация
регистрации → сотрудники по ID → заказчики по ID → новая заявка → событие/
результат квитанции → commit. Не получать координацию регистрации после
блокировки существующей заявки. Обновление выбранных ID без регистрации
сохраняет прежний порядок заявка → спецификации по ID. Тарифы публикуются
отдельно; файлы, UI, личные preferences и отчёты вне транзакции.
Разрешение имён, выделение защищённого UNIQUE номера и создание заявки —
одна фиксация; ошибка откатывает также новые справочные сущности.

Это проект для проверки выбранного Jet/ACE, не добавленная таблица или
обещание поведения провайдера. До внедрения проверить: два клиента создают
одинаковые/разные имена, регистрация профиля одновременно с заявкой, смена
порядка сотрудников/заказчиков, занятость соседней страницы, rollback,
deadline и обрыв commit. Ограниченное ожидание занятости не превращается в
повтор неизвестной записи; после обрыва исход проверяется по command_id.

### Несколько SELECT без обещания MVCC

BEGIN TRANSACTION сам по себе не означает PostgreSQL repeatable-read снимок.
Нужен нативный тест выбранного провайдера. Первый кандидат:
- Q1 возвращает ID/content_version порции, Q2 читает её текущие данные;
- повтор Q1 с теми же условиями/курсором подтверждает тот же состав,
  порядок и content_version всех строк;
- Q3 проверяет content_version одной заявки до/после набора SELECT;
- все команды записи увеличивают маркер в той же транзакции, что данные;
- собственные снимки/версии справочников проверяются отдельно, если чтение
  включает изменяемые подписи;
- при расхождении ответ не применяется; допустимо одно ограниченное
  перечитывание только read-операции, с отменой/проверкой поколения;
- при повторной гонке остаются прежние данные и понятный запрос обновления,
  частичный набор не выдаётся за актуальную карточку.

Повтор одного root-токена не доказывает неизменность состава страницы:
для списка нужен повтор именно Q1, иначе пропустим новую подходящую заявку.
Механизм предполагает соблюдение протокола всеми писателями Workflow и
отсутствие dirty reads. Прямая внешняя правка Access в обход маркера этим
протоколом не покрывается. Видимость commit, длительность/стоимость чтений
и вмешательство чужого клиента проверяются до внедрения.

## 8. Обновление экрана

Первый вариант перечитывает текущий ограниченный запрос Q1/Q2. UI сравнивает
ID/content_version, сохраняет выбор/ввод/прокрутку; исчезнувшая запись
обрабатывается явно. Смена фильтра/страницы отменяет применение прежнего ответа.
Контекст запроса — часть проверки поколения, одного CancellationToken мало.

updated_at, event ID и sequence не используются как надёжный watermark
порядка commit: транзакция с меньшим значением может завершиться позже.
Глобальную доставку дельт/удалений нельзя строить как WHERE id > last_id
без отдельного доказанного протокола. При этой нагрузке ограниченное чтение
предпочтительно оценить до введения такого протокола. Обновление не выполняет
DDL, не пересчитывает старые цены и не переписывает готовое письмо.

## 9. План измерений и критерии правильности

Предлагаемый синтетический стенд (числа не выданы за фактические данные):

- малая БД для проверки форм/пустых и неполных заявок;
- запас нескольких лет: 60 тыс. заявок, 300 тыс. спецификаций,
  1,2 млн версий, 1,5 млн событий; распределение по дням/сотрудникам неравномерно;
- стресс роста: 100 тыс. заявок, 500 тыс. спецификаций, 2 млн версий;
- отдельная большая заявка и спецификация с длинной историей;
- 1/5/10 клиентов: преимущественно чтение, независимая запись, одновременная
  запись разных спецификаций одной заявки и конфликт одной спецификации.

Сначала correctness: точные цены, NULL/0, ready/incomplete, один текущий
снимок, отсутствие умножения сумм JOIN-ом, составные FK, запрет изменения
истории, отмена, no-op, повтор command_id, обрыв до/во время/после commit.
Проверить архивирование во время открытой формы и публикацию тарифа во
время правки исторического расчёта. Конфликт сохраняет ввод.

Для каждого Q1–Q10: время, возвращённые строки/байты, число SQL-команд,
повторных чтений, обращения к файлу/сети и память клиента; план/страницы —
там, где их действительно даёт диагностика выбранного провайдера.
Раздельно фиксировать БД/движок, транспорт хоста, сеть, преобразование и UI.
PostgreSQL EXPLAIN не используется для доказательства плана Access.

Сравнивать холодный/прогретый кеш, локальный диск/SMB, короткий/широкий поиск,
редкие/частые материалы, первую/позднюю порцию, несколько лет истории.
Большой тестовый набор может упереться в 2 ГБ: это измеренная граница
выбранного формата, не повод обещать бесконечную историю в одном файле.
Замерять размер таблиц/индексов и рост на версию/событие; регламент архива
потребует отдельного согласования, автоматическое удаление истории не вводим.

Домашние копии и перенос их изменений отложены по поручению пользователя;
текущий набор проверок относится к общему рабочему файлу и резервированию.

Предварительные цели для согласования на выбранном оборудовании/LAN:
Q1+Q2 и Q3 p95 до 300 мс от клиента, явное сохранение до 500 мс без ожидания
чужой блокировки. Это проектные ориентиры, не измеренные результаты и не
гарантия. Для занятости/отказа задаются отдельные deadline и понятная причина.
Локальный Linux-замер не подтверждает Windows/SMB или работу установленного
продукта; выбранная архитектура проверяется реальными Windows-клиентами.
