## Основные чтения

| Запрос | Результат |
| --- | --- |
| Список | Порция ID/номеров/дат, заказчик/менеджер/ответственный, создатель/цвет, БЛЦБ, служебная версия |
| Итоги порции | Числа проектов/готовых расчётов/ожидающих позиций и сумма только для ID показанных заявок |
| Карточка | Реквизиты, позиции, проекты и выбранные варианты, актуальные спецификации/расчёты |
| Обновление отчётов | Пути нужных проектов, параметры текущего расчёта и базовые поля последнего принятого отчёта |
| Тарифы | Нужный небольшой каталог станков и ставки категории/толщины; кеш до явного обновления |
| Корзина | Порция удалённых заявок с их устойчивыми ID и служебными версиями |
| Сотрудники | Доступные технологи для выбора; имена/цвета связанных скрытых людей для отображения авторства |

Нет чтения всех заявок и подробностей всех проектов при старте, N+1 на каждую
строку или перечитывания каталога на каждую введённую цифру коэффициента.
Большие наборы загружаются порциями, ограниченными ID владельцев.
Сам принятый HTML/PDF читается только при подборе/принятии/открытии документа.

## Период, порядок и порции

Период относится к локальному дню CreatedAt заявки, а не к дате изменения или
документа. Для SQL — полуоткрытый диапазон начала/конца выбранного дня;
правило часового пояса и хранения UTC должно быть проверено до внедрения.
«Все даты» снимает диапазон. Журнал показывает недавние изменения первыми;
для SQL требуется устойчивый порядок updated_at + order_number и соответствующий курсор.

Начальная порция, например 100 заявок, уточняется по замерам. Не использовать
OFFSET-проход по всей таблице при глубокой навигации. Курсор содержит значения
последней строки выбранного порядка; параметры дат/сотрудника/поиска входят
в идентичность запроса. Ограничение порции применяется после фильтров.

Итоги относятся к тем же ID/служебным версиям, что и список. На Access чтение
несколькими SELECT само по себе не объявляется MVCC-снимком: проверять версии
и состав до/после и ограниченно повторять только чтение при изменении.
Поздний результат предыдущего периода/поиска не подменяет новый экран.

## Итоги без размножения строк

В сумме участвуют только включённые позиции, их выбранные неудалённые проекты
и актуальные расчёты. Исключённые и удалённые проекты не дают цену/готовность.
Неготовая позиция считается ожидающей, отсутствие расчёта не превращается в 0.
Варианты проекта сохраняются отдельно, но не складываются все сразу.

Сначала получить набор расчётов выбранных проектов, затем агрегировать по
заявке. Не JOIN-ить одновременно все проекты, документы и прочие дочерние
наборы перед SUM: это умножает деньги. Количества и суммы можно получать
раздельными агрегатами одной короткой операции хоста для ограниченной порции.
SQL не пересчитывает формулу и не подставляет текущий тариф вместо сохранённой
цены. Цены и итог берутся из актуального сохранённого расчёта.

## Универсальный поиск

Реализованный смысл поиска сохраняется:

- Фрагменты номера заявки/БЛЦБ, заказчика/менеджера, технолога/создателя,
  имени проекта/спецификации, станка, материала и сохранённых параметров.
- Несколько слов — AND между словами; каждое может встретиться в другом поле
  или другом проекте той же заявки.
- Учитываются все неудалённые варианты, включая исключённые из итога;
  корзина проектов/заявок не попадает в обычный поиск.
- Точный номер заявки ищется отдельно. Начало нового поиска снимает период;
  последующий выбор даты сохраняет текст и сужает набор.
- Лупа, очистка крестиком/Esc, Ctrl+F, число результатов и пояснение совпадения.

В JSON поисковая проекция кешируется по неизменному снимку workspace; ввод
фильтрует память без I/O и искусственного debounce. Старых редакций в данных
больше нет. Принятые отчёты и рабочие папки не сканируются при наборе.

Для Access: debounce около 300 мс, Enter сразу, отмена предыдущего чтения,
номер поколения ответа и ограничение порции. Поиск не блокирует UI. Каждый
терм параметризован; литеральные %, _, [, ?, * обрабатываются по фактическому
режиму LIKE выбранного провайдера. OleDb-параметры имеют правильные типы и
позиционный порядок, даты/имена не собираются конкатенацией SQL.

Совпадения дочерних данных проверяются EXISTS либо отдельным ограниченным
набором ID, без дубликатов заявок. Фильтрация до TOP/порции. Типизированные
нормализованные поля можно индексировать; нельзя обещать index seek для
LIKE с ведущим wildcard. При этой нагрузке небольшое сканирование проекции
допустимо после замеров. Отдельный полнотекстовый движок пока не нужен.

## Индексы

| Назначение | Кандидат |
| --- | --- |
| Деловой номер | orders(reference_number) UNIQUE |
| Период | orders(created_at, id) |
| Общий порядок | orders(updated_at, id) |
| Мои заявки | orders(technologist_id, created_at, id) при востребованном фильтре |
| Корзина | orders(deleted_at, id) |
| БЛЦБ | orders(blcb_number), не UNIQUE |
| Позиции | order_items(order_id, item_no) UNIQUE |
| Варианты | cutting_projects(order_item_id, variant_no) UNIQUE |
| Спецификация | specifications(project_id) UNIQUE при наличии проекта; FK order_id |
| Расчёт | specification_calculations(specification_id) PK/FK, если отдельная таблица |
| Тариф | cutting_rates(machine_id, material_group, thickness_mm) UNIQUE |
| Справочники | Нормализованное имя для поиска кандидатов, не безусловный UNIQUE фамилии |

Составные FK защищают принадлежность выбранного проекта позиции/заявке.
Один индекс не обязан одновременно обслужить диапазон по созданию и порядок
по изменению: фактический план/порядок/сортировку измерять на Access.
Не добавлять индекс к каждому полю из универсального поиска.

## Сохранение и блокировки

Форма хранит исходный снимок и ожидаемую служебную версию. Соединение и
транзакция открываются только на короткую запись. Не держать их при диалогах,
парсинге, проверке файлов, копировании HTML/PDF или работе технолога.

Базовый порядок транзакции Access (перед ним короткий служебный токен metadata):

1. Проверить действующего автора и условно обновить строку заявки по ID,
   ожидаемой версии и признаку корзины; проверить число затронутых строк.
2. Проверить принадлежность позиции/проекта, материал, тариф и параметры.
   Разрешение свободного имени менеджера — здесь же, а не отдельный INSERT
   перед записью реквизитов. Неоднозначность отклоняется.
3. Вставить/обновить актуальные параметры и расчёт, связь с последним принятым
   отчётом, состав/выбранный проект. Никаких новых редакций или событий.
4. Зафиксировать транзакцию. Ошибка до commit откатывает всю операцию,
   включая служебную версию и регистрацию нового имени.

Порядок блокировок одинаков: заявка → дочерние записи по ID. Каталог/прайсы
имеют собственный короткий путь записи и проверку снимка. Access может
блокировать страницы и соседние строки: отсутствие дедлоков не обещается
без нативных конкурентных испытаний. Нет глобальной блокировки всей БД.

Полностью неизменённое сохранение — no-op. Локальный JSON store разрешает
имена против актуального снимка под одной файловой арендой; хранилище и
preferences не блокируются вложенно. При занятости ошибка возвращается
быстро, ввод остаётся в форме; повтор записи не выполняется автоматически.

При неизвестном исходе сохранять черновик и устойчивые ID, явно сверять
фактическое состояние/версии. F5 с узким фильтром не доказывает отсутствие
созданной заявки. Техническая квитанция идемпотентности может быть добавлена
для Access после отдельного обоснования; общей ленты команд для MVP нет.

## Обновление интерфейса и проверка

Смена поиска/периода и чтение справочников сохраняют открытую карточку,
ручное письмо и черновики. Подтверждённое включение позиции обновляет строки
на месте без Reset/пересоздания карточки. Изменение поиска не снимает ручной
ввод. Автообновление общего журнала — будущий этап после Access-адаптера.

Измерять первый экран/поиск/открытие большой заявки/обновление отчётов,
число запросов/строк/байтов, задержки и конфликты 5–10 клиентов. Проверять
разные размеры и распределения данных, рост файла, разрывы SMB и закрытие
провайдера. Строить сценарии без старых редакций и событий. Проверки JSON,
headless UI и синтетический поиск не заменяют Windows/SMB/Jet/ACE испытаний.
