## Запуск

Открыть эту рабочую папку в VS Code, выбрать «Journal Workflow» и нажать F5.
Существующее окно VS Code в прежнем checkout запускает прежний Journal.

На этой Linux-машине подготовлено общее локальное окружение:

```bash
code --new-window /home/denis/Myprojects/journal/.local/Journal-development.code-workspace
```

В «Запуск и отладка» (`Ctrl+Shift+D`) выбрать перед F5:

- **Journal Workflow · новый подход** — сборка и запуск из отдельного worktree.
- **Journal · прежний вариант** — сборка и запуск из `/home/denis/Myprojects/journal`,
  с его прежними настройками и данными. Локальный фикс корзины остаётся там.

Каждый запуск собирает свой проект в своей папке; переключать Git-ветку для
этого не нужно. Остановить отладку — Shift+F5. Файл окружения хранится в .local,
не входит в релиз и не навязывает другим компьютерам абсолютные пути.

```bash
dotnet restore Jornal.Workflow.slnx --locked-mode
dotnet run --project src/Jornal.Workflow.Desktop -c Release --no-restore
```

### Компоновка списка и карточки · 24.10.2026

По поручению пользователя журнал и подбор переведены на две вертикальные
области с регулируемым разделителем (примерно 40/60 с минимальной шириной
карточки). В журнале слева компактная таблица заявок и поиск, справа карточка
с вкладками «Проекты», «Спецификации», «История», «Письмо». Строка открывает
карточку сразу; прежний переход на отдельный экран/кнопка «К заявкам» не нужны.
Реквизиты раскрываются в шапке. Поиск не выбрасывает текущую карточку,
даже если она перестала попадать в список найденных.

В подборе слева привычные имена проектов/позиция/состояние/стоимость,
справа параметры выбранной спецификации в две колонки. Галочка меняет
включение в пакет, сохраняя текущую просматриваемую карточку; щелчок по строке
переключает карточку. Список и поля прокручиваются независимо, цена и ручной
коэффициент остаются видимыми внизу карточки. Общее «Сохранить готовые (N)»
сохраняет прежний пакетный смысл. HTML использует базовый тариф; категория
HansLaser отображается отдельно по прежнему MVP-правилу.

Редактор существующей спецификации также использует две колонки и закреплённую
полосу стоимости/коэффициента/сохранения. Дополнительные тарифы и комментарий
раскрываются отдельно. Номер/дата новой ручной спецификации раскрыты сразу.

## Редактирование станков и тарифов

**Верхняя кнопка «Станки и цены»**. Слева выбрать станок; справа изменить имя или
формат импорта. Для тарифа выбрать строку и править поля под таблицей.
«Добавить толщину» создаёт строку с ценой пробивки 1 ₽. «Убрать тариф» убирает
строку из текущего прайса; исторические расчёты остаются. Все изменения
применяются одной кнопкой «Сохранить»; «Отмена» закрывает без записи. Можно
добавлять станки. Удаления станков пока нет, чтобы не терять ссылки.

Станок имеет постоянный UUID. Тариф и параметры спецификации связаны по
MachineId; Name — отображаемое название. Сохранённые версии содержат снимок
прежнего названия и цены. Переименование обновляет подписи открытой формы без
изменения суммы/dirty-состояния и не создаёт версию расчёта. Следующая осознанная
правка спецификации сохраняется уже с текущим названием. Повторный импорт
находит станок по LegacyKey (`legacy:…`/`table:…`), сохраняя локальное имя и
настроенный профиль импорта. Название не является внешним ключом.

Уникальность названий проверяется без учёта регистра. В рамках одного ID
станка и категории материала толщина не повторяется. Толщина положительна,
цены неотрицательны, пробивка задана явно. Проверка и сохранение всего
каталога атомарны под прежней локальной блокировкой/версией; окно редактирования
не держит файл открытым. При конфликте введённые изменения остаются в окне.
Неизменённые данные не записываются повторно. Перед изменением каталога
сохраняется резервная копия собственного workspace.

Локальная схема теперь **2**. При первом чтении схемы 1 создаётся `.bak`,
затем однократно назначаются ID во всех тарифах/версиях спецификаций. Даты,
номера, суммы, авторы и данные заявок не меняются. Следующее чтение использует
те же ID; ошибка миграции не подменяет файл пустым журналом.

### Лаконичный CI нового продукта

Один обязательный job Windows на pull_request, push в main и ручной запуск:
locked restore → Release build → Workflow-тесты → проверки идентичности/
сценариев упаковки. Сохранять TRX и логи; кешировать NuGet, отменять устаревший
CI одной ветки. Первоначально не вводить матрицу ОС и сложный вычислитель
состава. Запускать обязательный workflow на каждом PR; path-фильтр всего
workflow может оставить required check в Pending.
[Правило GitHub](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks).

Разработка и быстрые headless-проверки на Linux продолжаются локально.
Для Windows импорт цен должен отдельно проверяться на синтетической MDB с
поставленным x86-хостом. После реализации новой общей БД добавить обязательные
нативные тесты её операций; пропуск из-за отсутствующего провайдера не считать
успешной проверкой адаптера. Точные команды этого шага фиксируются при переносе,
после отделения зависимостей, а не подменяются проверкой JSON.

### Выпуск только Windows

Отдельный Release запускается явным тегом нового продукта либо вручную для
проверки упаковки. Только win-x64; x86-хост Access внутри поставки при наличии
зависимости от Jet. Никаких Linux-пакетов. Для точного commit/tag: сборка и тесты,
проверка product ID/канала/репозитория, упаковка, установка OfflineSetup,
проверка установленного хоста и обновление/перезапуск предыдущей установленной
версии. Затем контроль состава файлов, SHA256 и публичного feed.

Изначально — черновик выпуска; публикация после проверок. Право contents: write
нужно только шагу/задаче размещения, обычный CI работает с contents: read.
[Права GITHUB_TOKEN](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions).
Не использовать упаковщик с жёстко заданными EXE/PackageId/репозиторием старого
Journal; выделить параметры нового продукта и отказ при несовпадении. Сейчас
workflow-product.json продолжает запрещать публикацию, updatesRepository=null.
Снимать блокировку только после реализации и проверки этого контура.
