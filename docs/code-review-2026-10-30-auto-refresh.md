# Ревью автообновления списка заявок · 30.10.2026

Поручение — проверить действующий механизм после локальных изменений UI,
без расширения настроек. Во время исходного ревью рабочий код не исправлялся;
риски ниже
воспроизведены отдельными тестами на штатных MemoryMdb/WorkflowMdbStore/VM.
Счётчик/страницы/фильтрация используют существующий протокол.

## Исправления после ревью

По отдельному поручению пользователя 30.10.2026 все три замечания исправлены
локально. Сеанс подбора больше не скрывается при смене версии заявки;
повторное открытие возвращает прежние кандидаты, файлы, конфликты и ввод.
Принятие и повторный подбор заблокированы с сообщением о конфликте,
исходная версия не повышается автоматически. F5 начинает новый подбор.
Неизменившаяся заявка допускает обычную повторную проверку с прежними правками;
черновик одной заявки не блокирует автообновление другой.

RetainIds актуализируются перед TryAccept: снимок, не удержавший уже выбранную
карточку, откладывается без подмены cache/списка. Следующий опрос удерживает
её ID, даже когда строка больше не проходит поиск. У открытого выбора станка
обновляется ItemsSource, затем выбор восстанавливается по ID (или очищается
при удалении); введённая толщина сохраняется. Нет новых I/O/подписок/таймеров.

Постоянные регрессии — WorkflowAutoRefreshRegressionTests (8 сценариев).
До исправления первая версия набора: 6 fail / 1 pass, те же ошибки ревью;
добавлена проверка повторного подбора в открытом окне. Результаты окончательной
проверки — `.local/auto-refresh-fixes/verification.json` и логи рядом.
Полный Release: 612 pass / 6 штатных skip, Python: 9 pass. После уточнения
текста о сбросе правок через F5 финальные 8 регрессий пересобраны и повторены.
Debug и win-x64 Release: 0 предупреждений / 0 ошибок.
Описания ниже относятся к состоянию до исправления; номера строк исторические.

## Подтверждённые замечания исходного ревью

### P1 — теряются ручные значения закрытого подбора спецификаций

Путь: открыть изменённую HTML-спецификацию, вручную исправить длину реза,
закрыть подбор без принятия → коллега меняет БЛЦБ этой заявки → автообновление
принимает новую версию → вновь открыть подбор. Значение технолога заменяется
значением из отчёта без подтверждения. В проверке «37» превратилось в «21».
При этом перед фоновым обновлением HasPendingEdits был true.

`WorkflowViewModel.AutoRefresh.cs:93` считает карточку изменённой только по
HasCurrentCardEdits и не учитывает черновик подбора. После смены сохранённой
версии `CurrentReportReview` в `WorkflowViewModel.Reports.cs:14` перестаёт
возвращать прежний сеанс. Следующий `CreateReportReviewAsync` получает
previous=null и создаёт подбор заново. Старые значения, конфликты и выбор
файла не передаются конструктору кандидата.

Требуется сохранять сеанс подбора для его заявки/исходной версии и явно
разрешать конфликт с новой версией. Автообновление и повторное открытие
не должны тихо заменять введённые значения. Ограничение к текущему подбору
важно: глобальная блокировка обновления из-за любого чужого черновика
не является нужным исправлением.

### P2 — смена выбранной заявки во время чтения даёт ложное удаление

Путь: поиск показывает A и B. Начинается фоновое чтение при выбранной A;
коллега уже изменил B так, что она больше не подходит под поиск. Пока идёт
чтение, пользователь выбирает ещё видимую B и вводит свои реквизиты.
Применённый снимок не содержит B, и программа показывает «Заявка окончательно
удалена в другом окне…», запрещая сохранение. Backend при этом содержит
активную B. Ввод сохранился, но карточка ошибочно требует восстановления
контекста вместо обычного конфликта/удержания выбранной заявки.

`RefreshAutomaticallyAsync` формирует RetainIds перед await
(`WorkflowViewModel.AutoRefresh.cs:63`), но не сверяет их с текущим выбором/
черновиками перед принятием (`:65`). Переключение карточки не меняет поколение
фонового чтения и не обновляет Query.RetainIds. Store сравнивает переданный
снимок со своим по-прежнему старым Query; проверка проходит. Затем отсутствие
заявки в отфильтрованном снимке трактуется как удаление (`:104–108`).

Требуется повторная проверка актуального набора удерживаемых ID до принятия.
При его изменении снимок нужно отложить/перечитать, сохранив выбранную
карточку и ввод. Само отсутствие строки в странице/поиске не доказывает
удаления открытой заявки.

### P2 — открытый список станков не получает обновлённый справочник

Путь: открыть «Добавить проект», ввести толщину → коллега добавляет станок
в общий каталог → автообновление успешно принимает снимок. Свойство
ProjectMachines уже возвращает семь станков, но ComboBox продолжает показывать
старые шесть. Выбрать новый станок из открытой формы нельзя.

`ApplyBackgroundSnapshot` заменяет _workspace, но при неизменной версии
заявки не вызывает RefreshProjects. Уведомление ProjectMachines находится
только в RefreshProjects (`WorkflowViewModel.Projects.cs:269`), а
NotifyPriceCatalog не сообщает об изменении этого свойства. У открытой формы
остаётся прежний массив ItemsSource.

Требуется уведомлять элементы выбора об актуальном справочнике, сохраняя
выбранный станок и введённую толщину. Перестраивать всю карточку или сбрасывать
форму ради обновления списка не нужно.

## Что устроено хорошо

- Один координатор на окно, один запрос в работе; обычная проверка версии
  раз в 15 с (файловое событие может вызвать проверку раньше), объединение
  событий, контрольная сверка каждые 5 минут.
- Наблюдается только MDB; отказ/пропущенные события компенсируются опросом,
  наблюдатель восстанавливается. Ошибки чтения увеличивают паузу до 5 минут.
- В скрытом/свёрнутом окне, при жесте, меню или модальном окне чтение/
  применение откладываются. Неактивное, но видимое окно продолжает работу.
- Отдельный кандидат store сохраняет live cache/cursor/catalogue до проверки;
  TryAccept использует неблокирующий захват gate. Foreground отменяет фон
  до ожидания gate; поздние ответы поиска/смены источника/закрытия отбрасываются.
- Подготовка схемы/DDL и повтор записи в фоне отсутствуют. OutcomeUnknown
  остаётся до явного F5. Повреждение/недоступность источника не очищают UI.
- Чтение постраничное в пределах загруженного диапазона; неизменённые записи
  переиспользуются, обычные правки карточки/результата и якорь прокрутки
  сохраняются. Таймер/наблюдатель/подписки освобождаются при закрытии.

## Свидетельства и границы

Штатные 28 сценариев автообновления проходят. Три новых контрпримера
подтвердили именно описанные эффекты; они архивированы вне активного
тестового проекта, чтобы не оставлять намеренно падающие тесты в дереве.
`.local/auto-refresh-review/counterexamples.cs.txt` и `confirmed-probes.log`;
проверка реального ComboBox — `catalog-counterexample.cs.txt` и
`catalog-confirmed-probe.log` в той же папке.
После удаления временных файлов штатные тесты пересобраны и повторены.

Проверка выполнялась на Linux: реальный FileSystemWatcher — локальный файл,
MDB — существующий протокольный двойник. Настоящие Windows/Jet x86/SMB,
обрыв подключения и несколько рабочих ПК этим прогоном не подтверждены.
Явных дедлоков/неосвобождённых обработчиков при просмотренных путях не найдено;
это не доказательство отсутствия всех возможных зависаний/утечек.

Рабочие БД/папки проектов не использовались. Исправления продукта выполнены
после ревью по отдельному поручению, описаны выше. Commit/push/PR/релиза нет.
Основной Journal не изменялся.
